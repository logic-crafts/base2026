# Base2026 private members security review

Checked: 2026-08-31. This is an independent, read-only review of the frozen
private members candidate. It covers the existing Worker, native D1 member
schema, Better Auth `1.7.2` runtime, private My Research UI, and release
builder. No source implementation, account, remote D1, Google Console,
deployment, or Git state was changed by this review.

## Gate result

**Code/security gate: PASS with non-blocking hardening findings.** No
critical/high authentication, origin, tenant-isolation, cookie, token-leak,
or public-D1-write issue was found in the checked candidate. Findings F-01 to
F-05 below remain release hardening items; F-02 is a privacy/lifecycle
residual and F-03 is an availability/privacy partition caveat.

**Release status: PENDING.** The local Worker-runtime callback is synthetic.
Live Google authorization, the production `AUTH_DB` binding and migrations,
production secrets, deployment, edge/observability retention, and a real
browser E2E were not executed here. The Google Console client is therefore not
claimed live or release-approved. Passkey ownership is not a blocker for this
review.

## Scope and checked surfaces

- Better Auth is pinned to `better-auth@1.7.2`; the lockfile resolves the
  matching `@better-auth/core` and `@better-auth/kysely-adapter` packages at
  `1.7.2`. Wrangler is `4.124.0`, Vitest is `4.1.11`, and the installed
  TypeScript is `5.9.3`.
- The reviewed core advisories for implicit account linking, stale sessions,
  and IPv6 rate-limit bypass are outside their published affected ranges for
  `1.7.2` ([GHSA-g38m-r43w-p2q7](https://github.com/advisories/GHSA-g38m-r43w-p2q7),
  [GHSA-2vg6-77g8-24mp](https://github.com/advisories/GHSA-2vg6-77g8-24mp),
  [GHSA-p6v2-xcpg-h6xw](https://github.com/advisories/GHSA-p6v2-xcpg-h6xw)).
  No Better Auth plugin surface is enabled in this slice.
- Private API scope is `/api/auth/*` and `/api/my-research/*`; the private page
  is `/my-research/`. Production activation remains explicit and disabled in
  the checked public Wrangler config (`MEMBER_AUTH_ENABLED=false`, no
  production `AUTH_DB` binding in this candidate).
- The private database is a separate native D1 binding. `DB` is used only for
  the eligibility `SELECT` in `findPublicSource`; no private route writes the
  public database.
- `src/member-prototype.ts` is a narrow Worker-runtime mount of the same
  request handler. It is not evidence of a deployed service.

## Findings and bounded recommendations

### F-01 — P2: UI Google URL validation is host-only

`templates/base2026-members.js:101-107` verifies HTTPS, the exact
`accounts.google.com` origin, and no userinfo, but does not require the Google
authorization path or assert `state`, PKCE `code_challenge`/`S256`, canonical
`redirect_uri`, or the exact scope. The backend-generated URL is constrained
and the Worker test asserts those fields, so this is not an observed login
bypass in the candidate. It is a defense-in-depth gap if a trusted response
is tampered with. Before release, require
`/o/oauth2/v2/auth`, the generated state/PKCE/canonical redirect, exact basic
scope, and no forbidden provider parameters in the UI guard.

### F-02 — P2: account deletion leaves pending verification rows

`src/member-research.ts:507-523` deletes owned research, account, sessions,
and user rows, but not `verification`. The table in
`migrations-members/0001_better_auth.sql:50-57` has no user foreign key, and
`cleanupExpiredMemberVerification` (`src/member-auth.ts:317-324`) runs only
when an auth route is subsequently called. An abandoned OAuth state can
therefore remain expired in the private AUTH_DB until later cleanup. It is not
exported, is not reachable through another user's API, and is short-lived
state rather than account data, but it is not a complete deletion cleanup.
Choose a bounded, state-safe cleanup strategy before making a full deletion
claim; do not delete unrelated in-flight users' state rows.

### F-03 — P2: missing or malformed edge IP disables the custom session bucket

`src/member-research.ts:174-185` returns no custom unauthenticated-session
rate key for a missing, malformed, or unsupported `cf-connecting-ip`. The
Better Auth runtime still has `disableIpTracking:false`, so it falls back to
its shared `no-trusted-ip` per-path limiter rather than skipping all rate
limiting. This is an availability/privacy partition caveat, not an
authentication or tenant-isolation bypass. Production must keep the Worker
reachable only through the trusted Cloudflare edge path and should monitor
the no-IP fallback; a deliberate fail-closed or separate bounded server-side
bucket can be considered if edge-header absence is possible.

The production factory uses `disableIpTracking:false` at
`src/member-auth.ts:235-238`. The independent test helper in
`tests/member-research.test.ts:46-58` sets it true only for Better Auth test
utilities and is not the production factory.

### F-04 — P3: exact freshness boundary differs by one instant

`src/member-research.ts:256-262` accepts `age <= 600 seconds`, while Better
Auth's sensitive-session freshness check rejects at `age >= freshAge`.
At the exact boundary, the custom account-delete check can be permissive for
one millisecond. Use a strict `<` boundary or one canonical package check if
the owner wants exact equivalence. The current 10-minute window and tested
stale-session rejection do not create a practical bypass beyond that boundary.

### F-05 — P3: cookie clearing has a runtime compatibility fallback

`src/member-auth.ts:394-441` transports all cookies with
`Headers.getSetCookie()` or legacy `getAll()`. The checked Cloudflare
workerd tests expose `getSetCookie()` and pass. If a future runtime exposed
neither API, the helper currently returns the response without a clearing
cookie. Keep the deployed runtime test or make that path fail closed rather
than silently claiming browser sign-out.

### Additional low-risk hardening

`research_items` carries both `userId` and `collectionId`, with separate
foreign keys but no composite owner constraint (`0002_member_research.sql:
17-31`). All current API writes and reads repeat the owner predicate, so no
API cross-owner path was found; a composite owner constraint would improve
defense against manual/legacy DB corruption. Collection/item list reads also
rely on the enforced 50/500 write limits rather than SQL `LIMIT`; the export
path is explicitly bounded.

## Data and observability boundary

- Provider access, refresh, and ID token columns are nulled by account hooks;
  `encryptOAuthTokens:true` remains enabled. `accessType:"online"` reduces
  refresh-token issuance but is not treated as a storage guarantee.
- Better Auth's required session bearer `token` is stored in the private
  `session` table. OAuth database state contains ephemeral state, callback URL,
  and PKCE verifier in the private `verification` table. Neither is included
  in the application export or response payloads. The private D1 binding must
  be access-controlled; this review did not inspect account access policies.
- `wrangler.jsonc:60-65` uses the supported
  `observability.logs.invocation_logs:false` shape. This prevents automatic
  invocation events, while deliberately structured application logs remain a
  separate responsibility. The app does not log callback URLs, query strings,
  codes, state, verifiers, cookies, authorization headers, or provider
  payloads. The public catch logs only a pathname and is unreachable for the
  private callback branch.
- A query-string redaction key was not added: the pinned Wrangler schema does
  not accept the separately managed API setting checked in the earlier stack
  research. Review deployed traces, Logpush destinations, and retention before
  live OAuth; post-ingestion query filters are not redaction.

## Recommended pre-release checks

1. Apply the two dedicated migrations to the owner-approved production
   `AUTH_DB`, verify a zero-change rerun, and confirm the public `DB` was not
   touched.
2. Run a real browser Google E2E with the exact production callback, then
   inspect response cookies, database token columns, structured logs, traces,
   and Logpush destinations for codes/state/verifiers/tokens.
3. Close F-01 and decide the bounded F-02 cleanup behavior; align the F-04
   freshness boundary and retain the deployed `getSetCookie()` compatibility
   check.
4. Exercise concurrent quota/idempotency requests, state replay and expiry,
   revoke/delete with old cookies, representative IPv4/IPv6 and no-IP edge
   requests, and production origin/host rejection.
